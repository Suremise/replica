# Replica architecture

Replica backs up and mirrors folders on Windows. It drives a bundled restic for versioned targets
and has its own mirror engine. This file records how the code is laid out and the decisions made
while building it.

## Layout

```
crates/
  replica-core/   platform-free: jobs, settings, engines, runs, history, strings
  replica-win/    Windows only (behind cfg(windows)): paths, volumes, shares, credentials, Task Scheduler
  replica/        the two exes: replica.exe (CLI, console) and replica-tray.exe (tray and window, GUI)
locales/en/       Fluent strings
installer/        the WiX installer
third_party/      restic's pin, checksum and licences (the exe is fetched, never committed)
assets/           icons
docs/             this file, the user guide, RELEASING.md
scripts/          build-only scripts (fetch-restic.ps1)
```

`replica-core` builds and tests on any OS (CI runs its tests on Linux). It reaches the platform only
through small traits that `replica-win` implements.

## Decisions

- **Two exes from one package.** A Windows exe is either a console or a GUI program. `replica.exe`
  is the console CLI, with real stdout and exit codes; `replica-tray.exe` is built with
  `windows_subsystem = "windows"`, so a scheduled run never flashes a console window.
- **Toolchain pinned** to Rust 1.98.1 (stable) in `rust-toolchain.toml`, for reproducible builds;
  move it deliberately. Edition 2024, resolver 3.
- **Dependencies** are declared once in `[workspace.dependencies]` and added only when the code needs
  them.
- **restic is bundled, pinned and verified.** `third_party/restic/VERSION` holds the version and
  restic's official SHA-256 of the Windows amd64 zip, and `exe_sha256`, that of the exe inside it;
  `scripts/fetch-restic.ps1` downloads it into `third_party/restic/bin/` (git-ignored), checks
  both hashes and fails on a mismatch. A copy already there is kept only when its SHA-256 is
  `exe_sha256` (its version proves nothing), else it's fetched again; `-VerifyOnly` fails instead,
  and `package.ps1` checks the copy it packages too. Development, tests and CI all use that
  script. restic's licences are in `third_party/restic/LICENSES.md`, generated by
  `scripts/audit-restic-licences.py`.
- **The licence gate** is `deny.toml`, run by `cargo deny check` in CI: MIT or equally permissive only,
  plus advisories, yanked crates and unknown registries or git sources. It checks the Windows
  build only (`targets`), which is what ships: other platforms' dependencies, such as egui's Linux
  accessibility stack (`zbus`), are never in the exe.
- **Unknown settings keys warn, never fail.** Rather than `deny_unknown_fields` (which fails) or a
  wrapping deserializer (which can't see inside tagged enums such as targets and steps), the loader
  serialises the typed settings back to a TOML table and reports every key in the file that isn't in
  it. That works at every depth.
- **One set of exclusion rules for both engines.** `ExcludeRules` turns each source's patterns into
  absolute globs once; the mirror walker matches against them and the restic driver passes the same
  globs as `--iexclude`. Patterns are limited to what both read the same way: no `{a,b}`
  alternation, and character classes of plain characters and ascending ranges only (`[!a]` negates
  in globset but not in restic). A source's own path is escaped as one-character classes (`[[]`,
  `[*]`), which both read literally. `tests/exclude_restic.rs` checks the pinned restic takes
  exactly the files the walker keeps; CI on Windows sets `REPLICA_REQUIRE_RESTIC=1` so it can't skip.
- **A drive target's path stays inside its volume.** Validation refuses a drive letter or prefix
  (`C:outside`, which Windows reads relative to C:'s current folder), a leading separator and `..`,
  and `resolve_target` checks again, so a joined path can never leave the chosen drive.
- **Settings messages are in Fluent; the settings file's comments aren't.** Settings, validation,
  schedule and exclude-pattern errors come from `errors.ftl` (its "Settings" section). The comments
  `to_documented_toml` writes into `settings.toml` stay English: they document the file's format
  and key names, which aren't translated either.

## Core: jobs, settings and the platform traits

`replica-core`'s modules:

| Module | What it holds |
|---|---|
| `job` | `Job`, `Source`, `Target` (a drive by volume ID or label, or a UNC share with a credential *name*), `Mode`, `Retention`, `BeforeStep`, `AfterStep`, and validation |
| `settings` | `Settings` and `AppSettings` (`schedule_mode` is `timer` by default; `task-scheduler` is opt-in); `parse`, `load`, `load_or_default`, `save`, `to_documented_toml`; unknown-key warnings; `SettingsError` (exit code 4) |
| `exclude` | the pattern rules, `COMMON_EXCLUDES`, `ExcludeRules` (`matches`, `is_excluded`, `restic_args`) |
| `schedule` | the schedule syntax (`daily 02:30`, `weekly mon,thu 21:00`, `every 6h`, `every 90m`), `next_after` and `is_overdue` |
| `platform` | the traits below, `resolve_target`, and in-memory fakes in `platform::fake` |
| `jobs_file` | jobs files: `to_toml`, `write`, `read`/`parse`, and the import `plan` |

**Jobs files** are `settings.toml`'s `[[jobs]]`, written by its own writer
(`settings::write_job`), under a header (`format = "replica-jobs"`, `version`, `replica_version`).
`jobs_file::write` stages the text in a temp file of its own beside the destination (a unique
name, created exclusively) and publishes it with one rename: replacing with `--force`, else a
rename that refuses an existing file in the same step, so nothing but a whole export is ever at
the path. std's rename always replaces, so the caller passes the no-clobber one:
`replica_win::files::rename_no_clobber` (`MoveFileExW` without `MOVEFILE_REPLACE_EXISTING`, in
`win32`; any file system, FAT and exFAT sticks too), or `jobs_file::link_no_clobber` (a hard link)
in core's reader check. Core's other tests claim the path with a new empty file and rename over
it: on Windows a file the hard link made can't be replaced for a moment while its removed temp
name is still held open, as by an antivirus scan. The replacing rename, here and in
`Settings::save`, is `settings::replace`: Windows refuses one for a moment while another rename
onto the same file is under way or something holds it, so a refusal (Access is denied, only) is
tried again after short, growing pauses, ten tries within about a second, before it's reported.
A file of another format or a newer version is refused whole; a job in it that can't be read is
an entry with its reason, and the rest still read. **No secret can reach one**: a job holds none
(a share's login is a name, a repository's password is in the secret store under a name made from
the target), and keys a file adds are ignored with a warning. Importing is `jobs_file::plan(file,
settings, choices, secrets, targets)`: per job a `Status` (new, name exists, invalid) and an
`Action` (add, replace, skip, not chosen, refused), with whether its repositories need a password
here and its drives are connected (the secret store and resolver only look), the commands it
runs, and the settings that result, which the caller saves. Jobs are taken in the file's order,
each validated alone and then beside the settings and the jobs imported before it, counting only
problems the settings didn't have already, so the preview is exactly what saving gives and a job
that fails validation is never imported. Every imported job is `enabled = false` (a deliberate
choice). *Replace* keeps the job's name here (history is by name); *copy* takes the
first free `Name-N` within `MAX_NAME_LEN`. A share login can't be named like a repository password
(`job::REPOSITORY_SECRET_PREFIX`, `Problem::CredentialReserved`), or a file could hand a
repository's password to a share it names as that share's login.

`docs/settings.example.toml` is a full example with a versioned job and a mirror job; a test loads it.

### The platform traits (`replica-win` implements them)

All three are `Send + Sync`. A thing that's merely missing is not an error: return `Ok(None)` or
`ShareStatus::NotAvailable`, and the run reports "skipped: target not available" instead of
"failed". Return `PlatformError` only when an OS call fails.

- **`SecretStore`** (Windows Credential Manager): `get(name) -> Option<Credential>`,
  `set(name, &Credential)`, `delete(name)` (deleting a missing one is fine). A `Credential` is an
  optional user name plus a `Secret`, whose `Debug` output is redacted; never log `expose()`.
  Settings only ever hold the *name*.
- **`TargetResolver`**: `locate_volume(&VolumeRef) -> Option<PathBuf>` returns the volume's current
  root, found by volume ID first and then by label (case-insensitive), so a drive that comes back on
  another letter still matches. `connect_share(unc, Option<&Credential>) -> ShareStatus` connects a
  UNC share for this user (already connected counts as connected).
- **`Notifier`**: `notify(&Notification)`, with a level, an optional job, a title and a body.

`platform::resolve_target(target, resolver, secrets)` combines them for the run: the volume's root
joined with the target's path, or the share connected with its login. A target's credential name
that isn't in the store is an error, since the settings point to something that isn't there.
`platform::fake` has `MemorySecretStore`, `FakeResolver` and `RecordingNotifier` for tests in any
crate.

## Core: the restic driver

`replica_core::restic` runs restic's CLI with `--json` and returns typed results. The
module docs are the API guide for the run orchestrator; in short:

- **Finding restic:** `ResticSearch::for_this_exe(settings.app.restic_path)` then `find()`: the
  settings override (if set, the only place looked; missing is an error), then `restic.exe` beside
  Replica's exe, then, in debug builds only, `third_party/restic/bin/`. Never `PATH`.
  `Restic::new(path)` asks its version and logs a warning unless it's the pinned one
  (`restic::pinned_version()`, read from `third_party/restic/VERSION` at build time).
- **The repository password** is stored in the secret store under
  `restic::password_secret_name(target)`: `replica:repo:drive:id=<volume id>:<path>` (or
  `label=<label>`), or `replica:repo:unc:<path>`, lower case. It follows the target, not its
  current drive letter. `Repository::from_store` reads it; `replica init` creates it through
  `replica_win::keys`, which uses this same name (see "Windows targets and secrets").
- **Passwords never reach a command line or a log.** restic gets the repository and password only
  through `RESTIC_REPOSITORY` and `RESTIC_PASSWORD`; every inherited `RESTIC_*` variable is removed
  first. Every command line is logged (`tracing`, target `replica::restic`), and a test checks a run's
  log never contains the password.
- **Operations:** `init`, `backup` (tagged with the job name, the job's exclusions, progress events
  and a `CancelToken`), `snapshots`, `ls`, `restore`, `forget` (`--group-by host,tags`, the job's
  retention) then `prune`, `check` (`--read-data-subset`), `unlock_stale`, and `opens` (`cat
  config`: whether a password opens the repository, for `replica key set`).
- **Restore** puts a file or folder at `<target>/<its name>` (restic's `<snapshot>:<parent>` with
  `--include /<name>`, the name escaped so `[`, `]`, `{` and `}` in it are literal; if nothing by
  that name comes back, it's an error). The target must be new or empty, and may not be a source or
  inside or around one unless the request allows it. That check is made on where the restore really
  writes: the target and sources are made absolute, `.` and `..` resolved, and their existing parts
  resolved through links and junctions; a path that can't be resolved fails the restore.
  `RestoreRequest::job` scopes the snapshot (`Restic::job_snapshot`): `latest` is the job's newest,
  and an ID (or its start) must be one of the job's own, so a repository two jobs share never gives
  one job's data to the other (`SnapshotNotFound` otherwise). Before restoring, `ls` must show the
  item in that snapshot, so a file already at the target can't pass for a restored one. With
  `allow_over_source` (`replica restore --overwrite`) the target may also hold files.
- **`restore_many`** (the window's selection) restores several items into one new or empty
  folder, each as `<target>/<its name>` like `restore`: the folder is checked once, before the
  first, and two items with one name are refused (`RestoreSameName`) before anything is restored.
- **`sample_files`** picks up to N of a snapshot's files, each equally likely, as `ls` streams
  them (reservoir sampling on `Line::Node`), so a large snapshot's listing is never held whole.
  `local_path` is the reverse of `snapshot_path` (`/C/Work` is `C:\Work`, `//nas/share` is
  `\\nas\share`).
- **Results and errors:** restic's exit codes map to `ResticError`: 10 is `RepoNotFound`, 11
  `Locked`, 12 `WrongPassword`; 3 is a backup that's `Ok` but `partial`, listing the unreadable
  files (the run's "partly"). `unlock_stale` runs plain `restic unlock`, which removes only stale
  locks.
- **Each restic command runs in a `platform::ProcessTree`:** the CLI and the tray give
  `Restic::with_tree` `replica_win::jobs::JobObjectTree`, the job object command steps use, so
  everything restic starts (SFTP or rclone helpers; local and UNC repositories start none) is in
  the job. Without one, `platform::PlainTree` holds restic alone. Both output streams are read on
  threads, and the cancel and restic's exit are checked every 50 ms whether or not the output is
  still open, so a cancel is seen at once, even while restic is quiet or has closed its output.
- **Cancelling** stops the whole tree and returns once the job reports no process left, then
  deletes the lock files that carry the killed restic's PID and this host's name: restic on
  Windows doesn't treat a dead process's lock as stale for 30 minutes, which would block the next
  prune or check. The repository stays consistent, since restic only adds files and writes the
  index last. A program restic leaves holding its output open is given 5 s after restic exits,
  then stopped with the tree; anything else left in the job is stopped when the command ends
  (kill-on-close). A tree that has to be stopped (a cancel, or such a program) and can't be is
  `ResticError::NotStopped`, returned at once, never passed off as cancelled or as success.
  Tests: `crates/replica/tests/restic_tree.rs`, with a stand-in restic that starts a PowerShell,
  checked through the job's own process list (restic and the PowerShell in it before the stop,
  nothing after) and by PID; the core's own tests in `restic/process.rs` cover a program that
  closes its output and keeps running, and trees that can't be made or stopped.
- **Tests** (`tests/restic_driver.rs`, pinned restic, temp folders): back up, change, back up,
  restore an older file and folder, forget, prune, check; a wrong password and a missing
  repository; a locked repository; a cancelled backup; unreadable files; and the password log check.
  `tests/common` finds restic and skips without it, unless `REPLICA_REQUIRE_RESTIC=1`.
- **Shared:** `replica_core::cancel::CancelToken` is the Stop signal for every engine.

## Core: the mirror engine

`replica_core::mirror` makes an exact copy of each source, deletions included. Its module
docs list the rules; in short:

- **Layout:** each source goes to `<target>\<the source's name>`, so adding a second source never
  moves what's there. The engine only writes and deletes inside those folders. Two sources with the
  same name are refused.
- **Refused before anything changes:** a missing source; a source with no files, or only excluded
  ones (a disconnected drive must never wipe its mirror); a drive or share root as a source or a
  target; a target that is a source or inside or around one (checked on real paths, as for restore);
  a source's folder in the target that is a link or junction; and a run that would delete more than
  the job's `mirror_delete_limit_percent` (default 30) of the target's files. The limit holds for
  any number of files; 100 is how a job allows any deletion.
- **Links and junctions are never followed:** in a source they're skipped and counted; in the
  target they're removed as links (never what they point to) and replaced. If one can't be removed,
  nothing is written beneath it.
- **Copying:** into a staging file created new for that copy alone (`.<name>.<unique>.replica-tmp`,
  opened with create-new, so it can't be an existing file or a hard link to one), then renamed into
  place. Small files use the platform's own copy (`CopyFileEx` on Windows, which keeps the modified
  time and attributes); files of 4 MB and more go a chunk at a time (progress, cancelling). Up to 8
  files at once. Read-only files are copied and replaced. Files aren't flushed to disk before the
  rename (it would cost several times the run time on 50,000 files); NTFS keeps the rename itself
  consistent. A staging file left by a crash is an extra, so the next run removes it.
- **Type conflicts are refused (a deliberate choice for v1):** where the source has a file and the
  target a folder, or the other way round, at any depth, the target's item is left exactly as it is
  (nothing renamed or deleted there, nor under it) and reported as "type conflict: resolve by hand",
  a "partly" result. Everything else still mirrors. Replacing automatically may come later.
- **Cancelling** stops between files (and between chunks of a large file): each file already in
  place is complete, staging files are removed, and so are the new folders still empty.
- **Comparing:** size and modified time within 2 seconds (FAT and exFAT keep 2-second times), or the
  content too (`Compare::Content`).
- **Deleting** comes after copying, one entry at a time, deepest first: files and links, then
  folders once empty. What the exclusions match is left alone in the target, and so is every folder
  above it; nothing is deleted under a source folder that couldn't be read.
- **Results:** copied, deleted (each file, link and folder), unchanged, skipped (links in the
  sources), failed (with each path and the reason: in use, access denied), bytes and duration;
  `partial()` is the "partly" result. Progress events count files and bytes.

### Native or robocopy: measured

`examples/mirror_bench.rs` (`cargo run --release -p replica-core --example mirror_bench`) builds a
tree of 50,000 files of 1 to 16 KB in 500 folders plus three 200 MB files, then times each engine
into its own target: the first copy, a run with no change, and a run after a small change (20 files
changed, 10 added, 10 deleted). robocopy ran with `/MIR /COPY:DAT /DCOPY:DAT /R:0 /W:0 /NP /NFL
/NDL /NJH /NJS /XJ`, single-threaded (its default) and with `/MT:8`.

Medians of three runs of the final code, 21 Oct 2026, Windows 11, 16 logical processors, source
and targets on the same Samsung 990 PRO NVMe SSD (`%TEMP%`), files warm in the cache. Other builds
were running on the machine at times, so single runs vary a lot (robocopy's single-threaded first
copy took 31 s to 83 s across all runs).

| Run | Native (8 workers) | robocopy `/MIR` | robocopy `/MIR /MT:8` |
|---|---|---|---|
| First copy | 44.8 s | 34.3 s | 17.0 s |
| No change | 0.28 s | 0.16 s | 0.06 s |
| Small change | 0.32 s | 0.26 s | 0.07 s |

How native got here: the first version, one file at a time with a read/write loop, took 83 s for the
first copy; the platform's copy for small files and 8 workers brought it to about 43 s. The safety
fixes (a staging file created new for every copy, links checked) cost little after that.

**robocopy is faster:** about 2.6 times on a first copy with 8 threads, 1.3 times single-threaded,
and a tenth to a quarter of a second on later runs of 50,000 files.

**The choice: native anyway**, because robocopy can't meet the mirror's other requirements:

- **it writes straight into the target file,** so a run that stops halfway leaves a half-copied file
  where a good one was. The mirror requires a copy to a temporary name and a rename, and the native
  engine does that with a staging file that can't be an existing file or a hard link;
- **the safety rails need the full plan before anything changes** (an empty source, the deletion
  share, links and junctions in the target, a file and a folder swapping places with the old one put
  back on failure), so both trees are walked first anyway, and robocopy would walk them again;
- **its per-file results are text in the Windows display language,** which would have to be parsed;
  the native engine has typed results and errors for each file;
- **it is Windows-only,** where the native engine is in the platform-free core and tested on any OS.

A scheduled mirror's usual run is a no-change or small-change one, which takes a third of a second
for 50,000 files. The first copy is where robocopy's speed would show; if that matters more than the
above, the decision is the maintainer's to revisit.

## Core: running a job

`replica_core::run` runs one job start to finish; its module docs are the guide for the
CLI and the tray. The pieces:

- **`run::run_job(job, &RunContext, &mut History, on_event) -> RunReport`.** `RunContext` holds the
  `Restic` (or `None`, which fails only versioned targets), the `TargetResolver`, the `SecretStore`,
  the logs and locks folders (the platform's paths) and the `CancelToken`. `RunEvent`s report
  progress for the tray: steps, each target starting and finishing, and restic's or the mirror's
  progress.
- **The lock:** `run::JobLock`, a file per job in the locks folder held with the OS's file lock
  (`File::try_lock`), so a run from the CLI, the timer and Task Scheduler never overlap, and a crashed
  process can't leave it held. A run that finds it held is `Skipped` ("already running") and does
  and records nothing.
- **The repositories' locks:** `repo_lock::acquire`, after the job's lock and before
  anything runs, takes a lock for each repository a versioned job uses and holds it to the end of
  the run (before steps, backup, `forget`, `prune`, verify), so jobs that share a repository take
  turns instead of failing on restic's lock. The key (`repo_lock::lock_key`) is the repository's identity,
  as for its password (volume ID, else label, plus path; or the UNC path) with the path read as Windows opens it
  (`paths::typed_components`: separators, case, `.`, `..` and trailing dots and spaces, so `m`,
  `./m` and `M.` share a key); a job's keys are taken in sorted
  order, so two jobs sharing two repositories can't deadlock. The lock is the platform's
  `repo_lock::RepositoryLocks`: `replica_win::repo_locks::NamedMutexLocks`, a named mutex
  `Global\Replica.Repository.<user SID>.<key digest>` (the password mutex's pattern: every session of the user,
  no admin rights, an abandoned mutex taken over), so the CLI, the tray, Task Scheduler runs and
  another session all honour it whatever folder they use. `repo_lock::FileLocks` (an OS file lock)
  is the portable one the core's tests use. A busy repository is **waited for**: polled every
  250 ms with the cancel checked, up to `Waits::turn` (the app's `repository_wait_minutes`, 2 h by
  default), with `RunEvent::Waiting(Wait::Turn { target, job })` naming the holder (each holder
  writes its job's name to `locks\repo-<digest>.holder`) and `RunEvent::Waited` when it's over.
  Past the bound the run is `Failed` ("Waited … min for docs to finish with …"), recorded and
  notified as failures are. `RunReport::waits` lists every wait, how long it took and how it
  ended (`ok`, `timed-out`, `cancelled`, `gave-way`), restic-lock waits too, on success and on
  failure (`--json`'s `waits`).
- **Queues never stall behind a busy repository:** Run all (`replica run --all`) and the
  tray's queue start the first job whose repositories are free (`repo_lock::pick_next`, probing
  with `is_free`), else the first. A run that's waiting is asked, each poll, whether a job queued
  behind it could run now (`RunContext::give_way`); if so it lets go of what it took and returns
  `RunReport::gave_way` with nothing done, logged or recorded, and goes back to the front of the
  queue. Its wait counts from its first try, across tries (the CLI's loop, and the tray worker's
  `first_tried`, via `runner::QueueTurn`). Within one process jobs still run one at a time.
- **restic work outside a run takes its turn too:** `replica verify`, `replica restore`,
  `replica init`, and the window's Restore, Test restore and Set up now take the target's lock
  with `repo_lock::acquire_target` (the job's name as holder, or "the Replica window" for Set
  up), waiting up to `repository_wait_minutes` as a run does. The CLI prints the wait; the window
  shows it in place of "Restoring…" or "Setting up…" (`Backend::waiting`, set by
  `LiveBackend` while it waits). Quick looks (`replica snapshots`, the window's snapshot list and
  folder browsing) don't take the lock: `repo_lock::retry_locked` retries restic's own lock
  (`restic unlock` for stale locks, then backoff) for up to 30 s (`LISTING_WAIT`).
- **Keeping things:** `Retention::keep_forever` makes a versioned job's runs skip
  `forget` and `prune` altogether (the run log says so); validation then needs no counts. A
  **pinned** snapshot carries restic's tag `restic::PINNED_TAG` (`replica:pinned`), and every
  `forget` passes `--keep-tag replica:pinned`, so it survives any job's retention (a pin belongs to
  one snapshot, so this is safe in a shared repository). `Restic::set_pinned` runs `restic tag
  --json --add|--remove`, which rewrites the snapshot: it returns the new ID from restic's
  `changed` message. `replica pin`/`unpin` and the Restore page's Pin/Unpin hold the repository's
  lock (`acquire_target`) and retry restic's own (`retry_locked`).
- **Overlapping mirrors are refused:** only versioned targets are locked, so validation refuses
  mirrors that overlap another mirror or a repository (`job::Problem::MirrorOverlapsMirror`,
  `MirrorOverlapsRepository`), comparing targets as configured, by `paths::typed_components`
  (drives by volume ID or label and path, shares by UNC path with `..` stopping at the share).
  Versioned jobs sharing a repository are allowed, the supported case. Limit: a drive named by
  its ID in one job and by its label in another has two identities, so those two don't take
  turns (repository passwords have the same limit).
- **restic's own lock is the backstop:** a restic outside Replica, or a lock left behind,
  can still lock the repository. A command that gets restic's exit code 11 runs `restic unlock`
  once (it removes only locks restic judges stale, never a live one, by design), then is
  retried with backoff (1 s, doubling to 30 s) for up to `Waits::restic_lock` (10 min), with a
  `Wait::ResticLock` event (and a `Waited` in the report, however it ends); then it fails with
  "stayed locked by another restic for … min". A
  backup that can't get its lock fails the target; a `forget`/`prune` that can't leaves the run
  `Partly` (the snapshot is made).
- **Order:** before steps; then each target in turn (resolve; restic backup, `forget` with the job's
  retention, `prune`; or the mirror); then after steps (`command`s, then `verify` for each versioned
  target that backed up, when due). A failed before step fails the run and nothing else runs. A
  target that isn't available is `Skipped`. A failed retention or after step makes the run `Partly`.
- **Results and exit codes:** `run::Outcome` is ok, partly, skipped or failed; the run's is the worst
  of its targets' and steps' (failed, then partly, then skipped, then ok). `Outcome::exit_code()` is
  0, 2, 3 or 1; `run::EXIT_USAGE` (4) is the CLI's own, for usage and settings errors. A run with no
  target that ran is failed, not ok.
- **`sqlite-snapshot`** (`snapshot::sqlite_snapshot`): SQLite's online backup in one step (one read
  transaction, so one point in time, while writers carry on in WAL mode) into a new file,
  `PRAGMA integrity_check`ed, then renamed over the last copy.
- **Replica owns the staging folder (a deliberate choice).** A step names only its database
  (`db`); its copy goes in Replica's data folder, `<staging>\<job>\sqlite-snapshots\<step n>\<file
  name>` (`RunContext::staging_dir`, from the platform's paths). Each step has its own folder, so
  same-named databases never meet. Before the steps run, the job's `sqlite-snapshots` folder is
  tidied to exactly this run's planned copies (`snapshot::tidy`): folders of steps since removed,
  a step's copy of a database it no longer names, and unfinished temporary files all go. A live
  database (or one of its files) anywhere inside Replica's staging folder is refused at plan time,
  by canonical path, so tidying can never remove one. An old settings file that still has
  `staging` gets an unknown-setting warning, and it's ignored.
- **The snapshot plan** (`snapshot::plan`), worked out before any step runs. Every database and
  source path is resolved to where it really is (`paths::real_path`: `.` and `..`, relative paths,
  links and junctions), and one that can't be resolved fails the run before anything runs:
  - every live database file (the database, `-wal`, `-shm`, `-journal`) is left out by exact path,
    as the step names it, by its real path and as each source that holds it spells it, so the
    engines match it however it's reached; a source that is one of them is dropped, and the
    mirror skips a file source an exact exclusion matches;
  - the job's `sqlite-snapshots` folder is added as a source (a mirror keeps it as
    `<target>\sqlite-snapshots`), so every copy is backed up whatever the sources' exclusions;
  - a live database file inside Replica's staging folder is refused (so a copy can never land on
    one either).
- **No console windows:** every child process (restic, a step's shell) is made by
  `process::command`, which sets Windows' `CREATE_NO_WINDOW`: a console program started from the
  GUI exe would otherwise get a console window of its own, flashing up during every run. Output is
  still piped as before. `replica_win::jobs::JobObjectTree` adds `CREATE_SUSPENDED` through
  `process::set_creation_flags`, since `creation_flags` replaces the flags rather than adding to
  them. `replica-core/tests/process.rs` reads the sources and fails on a `Command::new` in shipped
  code outside the helper; `replica-win/tests/no_console.rs` starts a child down each path (the
  helper, the job object, a step's `cmd`) from a parent with no console (`DETACHED_PROCESS`, as
  the tray) and checks each has no console window. Shell actions (opening a folder, a log, Task
  Scheduler) use `ShellExecuteW`, which opens no console.
- **`command` steps** (`steps::run_command`): through `cmd /D /S /C` on Windows (`sh -c`
  elsewhere), output into the run's log; a non-zero exit code or the timeout fails the step.
  **Each command runs in a `platform::ProcessTree` (a deliberate choice): on Windows,
  `replica_win::jobs::JobObjectTree`, a job object with kill-on-close.** The shell is created
  suspended, put in a new job and only then resumed, so nothing it starts escapes the job. A
  timeout or cancel terminates the job and returns only once the job reports no process left; the
  end of the step closes the job, which ends anything still in it (even if Replica stops). A job
  that can't be made, assigned or stopped is the step's error (`StepError::Spawn` or
  `NotStopped`), never ignored. Tests check the tree through the job's own process list. Waiting
  for output after the shell exits is bounded by the timeout. `platform::PlainTree` (the
  program alone) is for tests that don't depend on stopping the tree.
- **The run history** (`history::History`, `history.db` in the data folder the caller chooses):
  SQLite with typed tables (`runs`, `run_targets`, `verifies`), versioned with `PRAGMA user_version`
  and migrated in transactions on open (3: `run_targets.skipped`, each target's count of files
  it couldn't back up or copy, NULL in older rows). `recent(job, limit)` for History and `replica status`,
  `last_success(job)` (the latest run in which a target backed up or mirrored, its own result ok
  or partly; a run whose targets were all skipped or failed doesn't count, whatever its steps did)
  for "overdue", and `last_verify` /
  `record_verify` for verify schedules.
  Migration 2 adds `test_restores` (`record_test_restore`, `test_restores(filter, limit)`),
  kept apart from `runs` so a test restore never counts as a job's last run for its schedule or
  "overdue". `runs(filter, limit)` and `test_restores` filter by job (any case) and outcome
  before the limit, and `job_names` lists every job in either table, for the window's History.
- **Test restores** (`test_restore`): up to five random files of the job's latest
  snapshot (`sample_files`) are restored, each into a scratch folder of its own (`run_in_temp`
  makes and removes it), and compared byte for byte with their sources (`local_path`). A source
  whose size or modified time differs from the snapshot's changed since and isn't compared; one
  that's the same size and time but other bytes is a **difference**: the backup doesn't hold
  what the source does. Any difference, or a file restic didn't restore, fails it; nothing
  comparable skips it. The window runs it and records it; the user guide documents it.
- **Logs:** one file per run in the logs folder, `<job>-<UTC time to the ms>-<pid>[-n].log`,
  created new so no run writes into another's: each step, its
  output, each target and its result, unreadable files, and the run's end. A summary line goes to
  the app log through `tracing`. No secret is ever written: restic's password only goes in its
  environment.

## The command line

`replica.exe` is `crates/replica/src/cli/` (a library module, so `replica tasks`
in `cli/tasks.rs` registers beside the others), with `src/bin/replica.rs` only calling
`replica::cli::main()`.

- **Commands**: `run <job>|--all [--quiet] [--json]`, `list [--json]`, `status [--json]`,
  `snapshots <job> [--json]`, `restore <job> <snapshot> <path> --to <folder> [--target]
  [--overwrite]`, `verify <job>`, `init <job>`, `key show <job> [--target]`, `key set <job>
  [--target] [--force]`, `login set <name> [--user]`, and `export [<job>…] [--all] -o <file>
  [--force]` and `import <file> [--only <job>…] [--on-conflict skip|copy|replace]`
  (`cli/jobs_file.rs`, over `replica_core::jobs_file`; `import` saves the plan's settings, and the
  tray picks them up as for any change to `settings.toml`).
- **Exit codes:** 0 ok, 1 failed, 2 partly, 3 skipped, 4 a usage or settings error (clap's own
  usage errors included; `--help` and `--version` are 0). They're in `--help`.
- **Help and messages** come from Fluent (`cli.ftl`): clap's derive gives the shape, and the help
  text is set from Fluent at start-up. `--json` (`docs/cli-json.md`) is versioned (`"schema": 1`)
  and never translated.
- **Where things are:** `replica_win::paths::AppPaths` (installed or portable): `settings.toml`,
  `history.db`, `logs\runs\` for run logs, `locks\` and `staging\`. Secrets in Credential Manager
  (`replica_win::credentials`), targets through `replica_win::targets::WindowsTargets`, command
  steps in `replica_win::jobs::JobObjectTree`.
- **`init`:** creates each target's folder; for a versioned target, if no repository is there yet,
  makes a password (`replica_win::keys::generate`), shows it once with the `password-save-*` text,
  and stores it only when the user types the confirmation word (`saved`); then
  `Restic::init_target` creates the repository and writes **`HOW-TO-RESTORE.txt`** in its folder
  (a deliberate choice): what the folder is, that any restic can read it with the password,
  and the `snapshots` and `restore` commands with this repository's path. It never holds a secret,
  and a copy the user has edited is never overwritten. The window calls the same
  `init_target` (see "The window").
- **`key set`** puts back a password the user saved (a new PC, a removed entry):
  `replica_win::keys::save_entered`, which saves it only once `Restic::opens` (`restic cat
  config`, no lock) says it opens the repository. A saved password that opens it is replaced only
  with `--force`, by one that opens it too; a saved one that doesn't is replaced. The check of the
  saved one and the write run under the keys lock. The window's "Enter a saved password…"
  (`ui/jobs/key_entry.rs`, through `Backend::save_entered_password`) is the same call.
- **`login set`** saves a share login under the `credential` name a share target gives it. Both
  commands read passwords with `replica_win::console::read_secret_line`: echo off on a console
  (`win32::console`), piped input as it is, and never on a command line or in a log.
- **`restore`** takes the path as it was backed up (`C:\Work\a.txt`) or as a snapshot shows it
  (`/C/Work/a.txt`), and refuses a `--to` that's a source, inside or around one, or not empty,
  unless `--overwrite`.
- **`--quiet`** prints nothing on success (for another app's run-on-close hook: `replica run projects --quiet`);
  problems still go to stderr. A progress line shows only when stdout is a terminal.
- **The language** is `REPLICA_LANG` if set, else the Windows display language
  (`replica_win::language::display_language`, which falls back to English); the tray does the same.
- **Tests** (`crates/replica/tests/cli.rs`) run the real exe with the pinned restic: its own
  `APPDATA` per test, a Credential Manager prefix of its own (`REPLICA_CREDENTIAL_PREFIX`, for tests
  only) whose entries it deletes, and drive targets on the temp folder's own volume by its volume
  ID, so they resolve for real. They run side by side: Credential Manager once lost a
  write when two processes wrote at once, even to different names, and every call now holds a
  per-user named mutex and reads a change back. A test can act as a second PC
  (`replica_on`: its own `APPDATA` and prefix), which is how the new-PC flow of `key set` is
  tested.

## Strings and languages

Every user-visible string, CLI messages included, comes from Fluent (`.ftl`) files in
`locales/<language>/`, through `replica_core::i18n`. `--json` keys are never translated. English is
the only language in v1, and the fallback for every key.

- **The files are compiled in** (`include_str!` in `crates/replica-core/src/i18n/embedded.rs`), so
  the portable copy needs no extra files. They are split by where the strings show: `common.ftl`
  (run results and skip reasons, used everywhere), `cli.ftl`, `tray.ftl`, `notifications.ftl`,
  `window.ftl`, `errors.ftl`, `tasks.ftl` and `installer.ftl`. The last is the MSI's own text,
  one plain line each: `scripts/package.ps1` passes it to WiX and checks the built MSI carries it.
- **No text in the code:** `crates/replica/tests/strings.rs` scans the three crates'
  non-test code. In a call that shows text (printing, the window's labels and buttons,
  notifications, errors meant for display), a string literal with a word in it, once its
  `{placeholders}` are out, fails the test; the rare literal that isn't prose (a file name) is
  allowed by name, with its reason. It's a heuristic: it sees only literals on the line of such
  a call, so text built elsewhere and passed along (an error's `to_string()`, say) isn't caught.
  Errors shown to users are worded in Fluent where they're made (core's `Display` impls) or where
  they're shown (a generic module's error at the app's boundary, as below); a review checks
  each new user-visible path. **Logs are diagnostics and stay in English**: the app log and the run
  logs, like restic's own output inside them, aren't translated.
- **Generic modules leave the wording to the app:** `replica_win::paths` (`PathsError`) and
  `ui::fonts` (`NoTextFont`) return what went wrong as data, and the app words it from Fluent
  (`cli::paths_error`, used by the CLI and `replica-tray --run`; the window's start-up), so the modules stay free of Replica's strings for other apps to copy.
- **The API:** `i18n::init(tag)` once at start-up, with the Windows UI language that `replica-win`
  reads (`en-GB`, `fr_FR` and the like); then `tr("tray-run-all")`, or
  `tr!("error-job-not-found", job = name)` with arguments (text or numbers). For a language
  other than the global one, build an `i18n::Localizer`.
- **Choosing the language:** an exact match for the tag, then the same language without a region,
  then any region of it, then English. A key missing in the chosen language falls back to English
  key by key.
- **Nothing fails silently:** a key missing in every language shows as the key itself and is
  logged (`tracing` warning), as is a message that doesn't format (a missing argument shows as
  `{$name}`). Syntax errors and duplicate keys are logged when the strings load.
- **Tests** (`i18n::embedded`): every file parses with no duplicates; every key has a value; every
  `.ftl` file on disk is embedded; other languages only have keys English has; and **every literal
  key the code passes to `tr(`, `tr_args(` or `tr!(` exists in English**. So pass keys as
  literals: a key built at run time escapes that check.
- No Unicode isolation marks around placeables: they show as stray characters in consoles and
  logs. A right-to-left language may want them back.

**Adding a string:** add `key = Text` to the right file in `locales/en/` (lowercase, hyphenated,
prefixed by where it shows: `cli-`, `tray-`, `notify-`, `tab-`, `error-`...), with a comment for
any argument whose meaning isn't obvious, then use `tr("key")` or `tr!("key", arg = value)`.
Plurals use a selector on a number argument (see `notify-run-ok-body`). Pass ready-made text for
durations, sizes and dates.

**Adding a language:** create `locales/<tag>/` with any of English's files (translated keys only;
the rest fall back to English) and add a `Locale` for it to `LOCALES` in `embedded.rs`; the tests
fail until every file on disk is listed there.

## Settings, data and logs

Two modules in `replica-win`, both generic (see "Shared with other apps").

**Where things live** (`paths`): `AppPaths::detect("Replica")` once at start-up, in both exes.
- **Portable** when a file named `portable` (empty, no extension) or a `settings.toml` sits beside
  the exe. A folder named `portable` doesn't count. Everything then lives beside the exe. Both exes
  sit in one folder, so they resolve the same place.
- **Installed** otherwise: `%APPDATA%\Replica\`, created if it's missing.
- **Not writable:** whether the folder can be written to is tested once, with a probe file that
  is removed straight away. (A folder's read-only attribute doesn't stop Windows creating files,
  so only a real write tells.) A folder that can't be written to is still the app's folder:
  `is_writable()` is false, so the CLI exits with code 4 (`error-portable-not-writable` or
  `error-app-folder-not-writable`) and the tray shows a notice and keeps settings in memory.
  **Nothing ever falls back to another folder.**
- `settings_file()`, `logs_dir()` (`logs\`), `run_logs_dir()` (`logs\runs\`) and
  `file(name)` (for the history database) give the paths; `mode()` and `is_writable()` are what
  the Settings tab and `replica status` show (strings `where-*` in `common.ftl`;
  `Mode::as_str()` gives `portable`/`installed` for `--json`).

**Logging** (`logging`): `logging::init(&LogConfig::new(Some(paths.logs_dir()), "replica"))`.
- **One app log file per process (a deliberate choice):** `<prefix>-<start time>-<pid>.log`,
  for example `logs\replica-2026-10-21-180000-1234.log`, with the time in UTC so the names sort.
  Only that process writes it, and it's never renamed, so processes running at once (two CLI
  runs, the tray and a scheduled `replica-tray --run`) never touch each other's logs. There is
  no shared, rolling `replica.log`: rolling one file between processes failed two reviews.
- **Cleanup** runs when logging starts: the oldest of that prefix's files beyond 20, or older
  than 14 days, are deleted (`LogConfig::retention`). Each process opens its file without delete
  sharing, so a log still open in another process can't be deleted and is skipped; cleanup never
  fails the app. A prefix only claims `<prefix>-<digit>…` names, so `replica` leaves
  `replica-tray`'s files alone.
- With no folder to write to (`dir: None`) there's no log file; `stderr: true` adds the console.
- Per-run logs go in `logs\runs\`, written by the run orchestrator. `logging::prune(dir,
  Retention { keep, max_age })` deletes the oldest beyond the setting's retention.

**Tests:** `crates/replica-win/tests/paths.rs` copies its own test exe into a temp folder, sets
up the marker, `settings.toml`, no marker (with `APPDATA` pointed at a temp folder) or a folder
everyone is denied writing to (with `icacls`, removed afterwards), runs the copy, and checks what
it detected. `tests/logging.rs` covers the subscriber, two processes logging at once (each
cleaning up as it starts) without touching each other's files, and cleanup by count and age,
of its own prefix only, skipping a file that's open.

## Windows targets and secrets

`replica-win` implements `replica-core`'s `TargetResolver` and `SecretStore` (`platform.rs`).

**`unsafe` lives in one module.** The workspace denies `unsafe_code`. Volumes, Credential
Manager and network connections are Win32 calls with no safe crate covering them, so
`crates/replica-win/src/win32.rs` alone allows it: thin wrappers that own every buffer they pass,
check the result, copy out what Windows returns and free what it allocated, each with a
`SAFETY` comment. Everything else calls those wrappers and stays safe.

**Drives (`targets`)**
- `list_volumes()` gives every volume's GUID path (`\\?\Volume{…}\`, what a target's
  `volume_id` holds), its label, mount points, file system, size and whether Windows calls it
  removable (many external hard drives report as fixed). It's for the window and `replica init`.
- `locate_volume` matches by ID first, in any form (`\\?\Volume{…}\`, `{…}` or the bare GUID,
  ignoring case), then by label, ignoring case. The drive's current letter is used, so a drive
  that comes back as `F:` instead of `E:` still matches. Two connected drives with the label
  asked for is an error, not a guess at which to write to. Not connected is `None`: the job is
  skipped.

**Shares (`targets`)**
- `connect_share` takes the share root (`\\nas\backup`) from the UNC path, then, all within 20
  seconds (`connect_timeout`):
  1. it probes the server's SMB port (445) for 3 seconds an address, if the name resolves here;
  2. it uses the share as it is if it's already reachable (the user's own connection, or no
     login needed);
  3. otherwise it connects with the stored login (`WNetAddConnection2`: no drive letter, not
     remembered after logoff).
- **Not available, so skipped:** the server or share isn't there, or the time runs out.
- **An error, so the job fails with a reason:** the login is refused (a wrong password, or the
  account locked or expired), or the share is already connected with a different login.
  Access is denied when no login is set.
- Connections Replica made are disconnected when the `WindowsTargets` is dropped (at the end of
  the run) or by `disconnect()`. A connection the user had is left alone.
- A connection that succeeds only after its time-out is still cleaned up. If the resolver is
  still there, it's recorded and disconnected with the others. If the resolver has gone, the
  worker thread that made it disconnects it. A `closed` flag, checked under the same lock as the
  list, decides which.
- The OS calls go through a small `Connector` trait, so unit tests drive these cases with a
  fake.

**Credential Manager (`credentials`)**
- `CredentialManager` stores generic credentials named `Replica/<name>`, for this user on this
  PC (they don't roam), with the secret in UTF-16 as Windows' own window stores passwords.
- So a NAS login can also be added by hand in Control Panel > Credential Manager > Windows
  Credentials > Add a generic credential, with the address `Replica/<name>`: `<name>` is what the
  target's `credential` setting says.
- Secrets leave the module only as a `Secret`, whose `Debug` output is redacted; nothing writes
  one to settings, logs or the history.
- **One call at a time, across Replica's processes:** Credential Manager loses changes
  made at the same moment, from parallel threads of one process or from separate processes (a
  write or a delete reports success and isn't kept, even to a read in the same thread). The
  tray's job thread reads credentials while its window writes them, and the CLI or a scheduled
  run can write beside the tray. So every `CredentialManager` call holds the named mutex
  `Global\Replica.Credentials.<user SID>` (across the user's logon sessions, like the
  repository passwords' mutex), and a write or delete is read back and made again, up to three
  times, if it wasn't kept: another app may change its own credentials at the same moment. The
  tests `parallel_writes_and_deletes_from_one_process_lose_nothing` (eight threads) and
  `parallel_processes_lose_nothing` (eight copies of the test binary), both checked through a
  fresh listing and `cmdkey /list`, fail without the mutex and pass with it.

**Repository passwords (`keys`)** work like this:
- `keys::generate(job, target, store)` makes a 30-symbol password (six groups of five, from 31
  letters and digits that can't be confused when copied by hand: about 148 bits) from
  `BCryptGenRandom`. **It doesn't store it.**
- The CLI or window shows it once (`NewPassword::reveal`, with the `password-save-*` strings)
  and asks the user to confirm they've saved a copy. Only `confirm_saved` stores it and hands it
  back for `restic init`, so a user who stops there leaves nothing behind.
- `keys::show` is the deliberate way to see it again (`replica key show <job>`) and is logged
  without the value. `keys::for_restic` is how a run gets it.
- `keys::save_entered` puts back a password the user kept (`replica key set`, the window's
  "Enter a saved password…"), only once the caller's `opens` check (`Restic::opens`) passes. A
  saved one is replaced only if it doesn't open the repository, or with `force`; the check of
  the saved one and the write run under the mutex below.
- An existing password is never replaced. Credential Manager has no "create if absent", so
  `confirm_saved` checks and writes under the named mutex
  `Global\Replica.RepositoryPasswords.<user SID>` (a deliberate choice). Its scope matches
  the credential's: Credential Manager keeps a password for this user on this PC, visible in
  all of the user's sessions (console, RDP, scheduled tasks). The `Global\` namespace spans
  sessions, and the SID is the same in all of them but differs between users. It's created with
  the user's own default security, so no admin rights are needed, and a mutex left by a process
  that died is taken over. Of two confirmations at once, only one stores, and the other is
  refused before its `restic init`. Another user on the PC could create a mutex with that name
  first and deny us access. Confirmation is then refused (`error-key-busy`): it's blocked, but
  no password is lost.
- **There's one name for a repository password:** core's
  `restic::password_secret_name(target)`, as in "Core: the restic driver" above. `keys::key_name`
  calls it, so the password `replica init` stores through `keys` is the one a run's
  `Repository::from_store` finds. In Credential Manager it appears as
  `Replica/replica:repo:drive:id=…:<path>` (or `label=…`), or as `Replica/replica:repo:unc:<path>`.
  The name follows the repository, so renaming a job or a target keeps its password, and two jobs
  that share a repository share its password.

**Tests:**
- Unit tests: matching volume IDs in every form, a drive moving from `E:` to `F:`, an ambiguous
  label, UNC parsing, which Win32 errors skip and which fail, UTF-16 secrets, and password
  generation and the confirm-before-store flow.
- Integration tests use the system drive as a drive target (found by ID and by label), shares
  that don't exist (`\\127.0.0.1\<no such share>` and a `.invalid` server, which never resolves,
  so no login is sent anywhere), and the real Credential Manager under a `ReplicaTest-<pid>-…/`
  prefix that each test empties when it ends.
- A real NAS (with a wrong password too) and an external drive on another letter are on the
  release checklist.

## The tray, notifications and schedules

`replica-tray.exe` (`crates/replica/src/tray/`) is a GUI program, so it never shows a console.
Its modes (parsed by `tray::Mode::parse`):
- **no arguments, or `--show`:** the tray app with its window open, as when the user starts it
  (the Start menu shortcut passes nothing; the installer's LaunchTray passes `--show`);
- **`--background`:** the tray app alone, its window closed: what Start with Windows runs;
- **a second start** while a tray runs, in either of those, signals that tray's Show event (its
  window comes forward) and ends;
- **`--run <job>`:** what a Task Scheduler task runs. It runs the job unless schedules are
  paused or the Task Scheduler option is off, notifies as the tray would, and exits with the
  job's code.

**The tray scaffold (`replica-win::tray`, generic):**
- **Its own notify icon:** a hidden tool window owns it (`Shell_NotifyIconW`,
  `NOTIFYICON_VERSION_4`), with a Win32 popup menu, and it re-adds itself when Explorer
  restarts.
- **Not `tray-icon` (a departure from the planned stack):** `tray-icon` can't show
  balloons, and balloons are the notifications that work in every mode, portable included.
  Windows toasts need an AppUserModelID, which a portable copy lacks. Owning the icon is a few
  hundred lines in `win32/ui.rs`, and `muda` isn't needed either.
- **Icons:** the `.ico` files from `assets/tray/` are compiled in (redrawn in the
  family style of the author's other tools, see `assets/README.md`). The image is picked for the icon's
  monitor DPI (the process is per-monitor DPI aware, v2). The light- or dark-taskbar variant
  follows `SystemUsesLightTheme`, checked on every loop; the two are drawn the same,
  a teal disc that reads on either.
- **Single instance:** a `Local\Replica.Tray.Instance` mutex, one per user session. A second
  launch sets `Local\Replica.Tray.Show` and exits, and the first wakes from its loop on that
  event.

**Notifications (`replica-win::notify`):**
- Balloons from the tray icon (`NIIF_RESPECT_QUIET_TIME`), queued from any thread.
- A failure always notifies, and so does a partly done run. A success notifies only if the job
  asks. A skipped run never does; an overdue notice covers a target that stays away.
- Overdue notifies at most once a day per job, and not while schedules are paused.
- `--run` has no tray, so it shows its notification with a temporary icon of its own for 10
  seconds.
- **The exes' version resource** (`crates/replica/build.rs`, with `embed-resource` and the Windows
  SDK's `rc.exe`) says "Replica" and carries the app icon, so notifications, Explorer and
  the taskbar show "Replica" rather than the exe's file name.

**The built-in timer (the default):**
- Every 15 seconds the tray works out, for each enabled job with a schedule, whether it's due:
  its schedule's next time after its last run (any outcome, so a failing job isn't retried in
  a loop), or after the tray started, for a job that never ran.
- So a run missed while the PC was off happens once, when the tray is back.
- Due jobs queue, and run one at a time on a worker thread through the same path as
  `replica run`: the same lock, history, resolver and secrets. Stop cancels the current run and
  clears the queue.
- It stands down while schedules are paused and when the option is Task Scheduler, and
  `--run` refuses while the option isn't Task Scheduler, so the two never both run a job. A
  per-job lock also stops a concurrent run from the CLI or a task.
- Each job's cancel token is made when it's handed to the worker. So Stop and Quit also reach a
  job that's been dispatched but hasn't started, which is then skipped with nothing done.

**Task Scheduler (`replica-win::scheduler`; an option, off by default):**
- Driven through its COM API (`ITaskService`), not `schtasks`, whose output is translated.
- Tasks live in `\Replica\`, one per scheduled, enabled job, named after it. Each runs
  `"replica-tray.exe" --run "<job>"`:
  - as the user, while they're logged on (`InteractiveToken`, no stored password, no admin);
  - one at a time;
  - catching up a missed start;
  - on battery too;
  - with no time limit.
- Daily and weekly schedules are calendar triggers at the local time. `every N` repeats every N
  from when the task was made.
- The task's `<Data>` records the job, schedule and exe, which `sync` uses to update only what
  changed and the list uses to show the schedule.
- `Scheduler::sync` makes the folder match the jobs, and keeps a task the user turned off
  turned off.
- **The saved option rules, whenever the tray loads the settings (at start too):**
  - **Task Scheduler on:** the tasks are synced.
  - **Off:** any task still on is removed (`delete_enabled`), so an option turned off while
    the tray wasn't running is honoured. Tasks the user turned off stay, which is what the
    window's "keep them" answer leaves.
  - This is `tray::runner::reconcile_tasks`. A leftover task that runs anyway finds `--run`
    refusing.
- Looking up a folder or task treats only "file or path not found" as "not there". Access
  denied, a stopped service or another COM failure is reported, so listing or removing tasks
  never claims success it didn't have.
- **"Nothing hidden" (a deliberate choice):**
  - `list` gives every task with its job, schedule, next and last run, last result and on/off,
    and flags **orphans** (tasks whose job is gone);
  - `set_enabled`, `delete` and `delete_all` manage them;
  - `turn_off(delete)` is what turning the option off does: delete them all (the window's
    default) or turn them off.
- The CLI has the same: `replica tasks list [--json]|enable|disable|remove <task>|remove --all`
  (`crates/replica/src/cli/tasks.rs`). The window has the same in Settings' Scheduled-tasks view.

**Start with Windows (`replica-win::autostart`):**
- An HKCU Run value `Replica`: the quoted path of the running `replica-tray.exe`, then
  `--background` (`tray::autostart`), so a login starts the tray without its window. The tray
  applies the setting at start and on every settings change: an entry that differs (a moved
  copy, or one an older version wrote without `--background`) is rewritten, and it's removed
  when turned off.
- It's only ever removed if it starts an exe named `replica-tray.exe`, so another program's
  entry of the same name is left alone.

**Tests:**
- The timer's due and overdue logic with a fake clock (`tray/state.rs`).
- Which runs notify, and the tooltip.
- A job whose lock a CLI run holds is skipped from the tray (`tray/runner.rs`).
- The `.ico` reader and every tray icon.
- Single instance, waking the first.
- Start with Windows in a test-only key (`AutoStart::in_key`, `HKCU\Software\ReplicaTest\<pid>-…`,
  deleted when the test ends), never the Run key: `--background` and rewriting an older entry
  included. The tray's arguments (`tray::tests`).
- Task Scheduler create, update, delete, enable, disable, orphans and turning it off, against
  the real service in a test-only `\ReplicaTest-<pid>-…` folder that each test deletes
  (`crates/replica-win/tests/scheduler.rs`).

**Release checklist:** on a real logon, check the icon in the notification area (Windows 11
puts a new app's icon in the overflow until it's pinned), the menu, the theme switch, and a
Task Scheduler run with no console flash.

## The window

`crates/replica/src/ui/`: egui through eframe, with the **glow** renderer and
**AccessKit** (so Narrator and other screen readers read it), and egui's `default_fonts` off
(their licences are OFL/Ubuntu, outside the licence rule).

**Threads.** The tray keeps its Win32 message loop on the main thread. "Open Replica…" (or a
click on the icon, or a second launch) starts the window on a thread of its own, the first time
(`ui::Window::start`; winit's `with_any_thread`). A process can make only one winit event loop,
so the window is never closed after that: closing or minimising **hides** it, and the tray shows
it again (`Window::show`). eframe still calls `App::logic` for a hidden window when it's asked
to repaint, which is how a show request gets through.

**When the window's thread can't answer.** A file dialog runs its own modal loop on the
window's thread, so nothing in the window runs until it closes. The dialogs are owned by the
window (`Backend::set_owner`, rfd's `set_parent`): they open over it, it's disabled underneath,
and minimising or restoring moves them together. If the window hasn't taken a show request within
`ui::SHOW_GRACE`, the tray brings it, and the dialog it owns, forward itself with Win32
(`Window::follow_up`, `replica_win::window::bring_forward`). That only takes if the window's
thread is pumping messages (a modal dialog's loop does), so the tray then checks that the window
shows and answers (`replica_win::window::responds`) within `ui::RECOVER_WITHIN`. If it doesn't
(the thread is stuck), or the window hasn't started within `ui::START_WITHIN`, the tray says so
in a notification, each time Open is tried. A panic on the window's thread is
logged (`logging::log_panics`, for every thread) and caught, so `Window::failed` says the window
stopped, and Open shows that instead of doing nothing. The log follows the window: started,
shown, closed or minimised to the tray, each file dialog opened and closed, Open and Quit.

**The window doesn't run anything itself.** It edits `settings.toml` and asks the tray
(`ui::backend::UiRequest`: `Reload`, `Run(jobs)`, `Stop`) over a channel the tray drains on
every loop. The tray reports back through a shared `ui::backend::Status` (what's running and at
what percentage, what's queued, each job's last run), and wakes the window when it changes. So
a job runs the same way from the menu, the timer and the window: one at a time, with the same
lock and history.

**`ui::backend::Backend`** is everything the window needs from outside: the settings file, the
tray, Credential Manager, the connected volumes, Task Scheduler, restic and the file pickers
(`rfd`). `LiveBackend` is the real one; tests give it temp folders and fakes.

**The shell (`ui/shell.rs`):**
- A left sidebar of the pages: Jobs, History, Restore, Settings (with the Scheduled-tasks view)
  and About, each a module shown by `Shell::tab`, with an icon from `ui/icons.rs`. The page shown
  has the accent's bar and a subtle fill. A screen reader reads the sidebar as a tab list
  ("Pages"), each page a tab with its selected state.
- Over the page, its header: the title (24 semibold) and a line under it (`page-*-subtitle`).
  The page is at most 880 points wide, 24 from the sidebar. The sidebar is 240 wide, 200 under
  a 1000-point window, and under 880 points a 56-point **rail** of the icons alone, each page's
  name in its hover text (and still its name for a screen reader).
- The sidebar's header is the app icon (20 points) and "Replica" at section size. `build.rs`
  decodes the icon's 20, 32, 40, 48 and 64 px PNGs from `assets/icon/replica.ico` to raw RGBA
  (`ui::app_icon` draws the one sharp at the display's scale), so the window decodes nothing
  at start-up. (The exe does carry `png` and `image` anyway: eframe's clipboard, `arboard`,
  uses them.)
- Closing or minimising sends it to the tray. The first time in a session it says so instead
  (`tray-notice-*`), with "Don't show this again".
- Its place and size, and that box, are kept in `window.json` in the app's folder
  (`ui/geometry.rs`), not in `settings.toml`. A saved place is used only if its title bar is
  still on a monitor (`replica_win::window::is_on_screen`).
- **The first time**, or with no usable saved place, it opens at 1180 × 780 points
  (`geometry::DEFAULT_SIZE`), less if that's more than 85% of the work area's width or height
  (never under the 720 × 480 minimum), centred on the work area of the monitor the pointer is
  on (`replica_win::window::work_area`; `geometry::first_rect` does the sums, and its tests
  cover a small work area).
- The title bar and taskbar use `assets/icon/replica.ico` (`replica_win::window::set_icons`).
- Text is Segoe UI Variable (Windows 11), then Segoe UI, loaded from `%WINDIR%\Fonts` at run
  time (`ui/fonts.rs`): no font ships. Semibold is a family of its own (`fonts::SEMIBOLD`): the
  variable font at `wght` 600, or Segoe UI Semibold. Monospace is Cascadia Mono, then Consolas.

**The look (`ui/theme.rs`)**, modelled on Windows 11 Settings:
- Two palettes, `theme::LIGHT` and `theme::DARK`, set as egui's two styles by `theme::install`
  (`ui::style`). egui's theme preference stays "system", so the window follows Windows' light or
  dark mode and switches while it runs. Widgets that draw their own colours take them from
  `theme::of(ui)`.
- Neutral greys, a raised card with a hairline border, a secondary text colour; the accent is
  Replica's teal (#0E7490, lighter in dark mode); status colours: green ok, red failed, amber
  skipped/overdue/partly, grey not run.
- **Every pair of text and background passes WCAG AA** (4.5:1; 3:1 for glyphs, outlines and the
  focus ring): `theme::tests` computes each ratio from the palettes, so a colour change that
  fails is caught.
- Type: page title 24 semibold (`TextStyle::Heading`), section 16 semibold
  (`theme::section_style()`), body 14, secondary 12. Spacing 4/8/12/16/24/32/40
  (`theme::space`), controls 32 high, 6-point corners on cards and 4 on controls.
- **Where the spacing goes (roomier after the first layout proved "a bit cramped")**, as named
  tokens in `theme::space`: page margins 32 (`PAGE_MARGIN`), 40 between the full sidebar and
  the page (`SIDEBAR_GAP`), 24 under a page's header (`UNDER_HEADER`), 16 between cards
  (`CARD_GAP`), 20 inside a card (`CARD_PADDING`), 12 above and below a setting row's contents
  (`ROW_PADDING`, and at least 52 high with a description: `ROW_MIN_HEIGHT`), 8 between a
  toolbar's controls and 12 between its groups (`TOOLBAR_GAP`, `TOOLBAR_GROUP_GAP`), and the
  sidebar's items 40 high, 4 apart (`NAV_ITEM_HEIGHT`, `NAV_ITEM_GAP`).
- The widget with the keyboard focus gets a 2-point ring (`theme::paint_focus`, once a frame).

**The components (`ui/widgets.rs`)**, each named for a screen reader:
`section_card` and `section_card_with_actions` (buttons at the right of its title), whose title
is a `heading` (read as one, so a screen reader can jump from card to card); `setting_row`
(label and description on the left, the control on the right, hairlines between rows). As in
Windows' own settings, the row *is* its control for a screen reader: the control is named by
the label and described by the description, and the text beside it is painted, not read a
second time. `info_row` is the same layout for a control that keeps its own name (a chip, a
link), with the text read beside it, and `path_row` an `info_row` with a `path_field`. Then
`primary_button`,
`secondary_button`, `danger_button` (a secondary button with red text and an optional icon),
`danger_button_filled` (only for a confirmation's last destructive step: "Delete", "Remove all",
"Discard changes", and the editor's "Use a mirror anyway" and "Replace it anyway"),
`icon_button`, `toggle` (an on/off switch, read as a
check box), `segmented` (a few options side by side, read as a radio group),
`relative_time` ("in 9 h", "2 h ago"), `status_chip` (`Tone`: each with its own glyph, so not by colour alone),
`path_field` (cut in the middle, full path in its hover text and its name, a copy button),
`empty_state`, `info_bar` (read as a status, or an alert for an error) and `table`.
`table` is over `egui_extras`' `TableBuilder`: header (a click on a sortable column's title
sorts; the caller sorts its rows by `TableState::sort`), striped rows, resizable columns, row
selection, an empty state. Like a Windows list it is one keyboard stop: the arrow keys, Home
and End move the selection, Enter activates; a screen reader reads a list box and its
selected row. Also: `secondary_button_with_icon`, `tag` (a grey pill for a kind),
`removable_chip`, `copy_field` (monospace text with a Copy button), `progress_chip` (a track
across the chip, filled as far as it's done, its text over both), `info_chip` (a live state in
the info colours), `message_bar` (an info
bar whose group is named by its text's own node, so the message is read once) and `steps`

A `table`'s rows are as tall as its tallest cell seen, plus 10 above and below, and never under 40 (a two-line cell gives about 54); each cell is centred in its row, so a one-line cell sits level with a two-line one. Every page (Jobs, History,
Restore, Settings, About) is built from these.
- **How the table takes clicks:** its cells have no spacing between them (each pads
  itself), so a click anywhere on a row reaches it, except on a column's border, where
  egui_extras' resize handle (the table's full height) takes it. A row's node in the
  accessibility tree is placed on its first cell, so a screen reader's (or a test's) click on

  is, for a page that scrolls and a screen reader that reaches each one. Sortable headers are
  named "Sort by <column>", apart from a filter named by the same word.
- `quiet_text` is a table cell's text drawn without a node of its own (the row is named with

  `egui::Modal`, with room round its contents (every dialog's: the Jobs page's through
  `jobs::dialog`). An `info_bar` is read as a status or alert
  holding its text, not named with it again.

**The Jobs tab (`ui/jobs/`):**
- A command bar ("New job", "Run all") over a `widgets::table` of the jobs: on/off (a toggle),
  the name with its mode as a `tag`, the last result as a status chip (why it failed or was
  skipped in its hover text: `backend::LastRun::reason`, the run's error else the first target's
  reason; while it runs, a `progress_chip`; waiting its turn, an `info_chip`), the last run and
  the next run said as Settings says times (`widgets::relative_time`: "9 h ago", "in 8 h"; a

  with the exact time in its hover text, the schedule and what runs it under the next run, and
  the targets (left out under 780 points). Sortable by name, status and last run; double-click or Enter opens the editor.
  Each row has Run now (Stop while it runs, with the progress in its status cell), Edit, and a
  ⋯ menu with Delete. With no jobs, an empty state with "New job". "Run selected" went with
  the old list's tick boxes: each row's Run now and "Run all" remain.
- Every change re-reads `settings.toml`, applies itself, runs core's validation over all the
  jobs, saves, and sends `Reload`. Nothing is saved while the file can't be read or the app's
  folder can't be written to; the tab says so.

- **The editor** (`editor.rs`, with the form model in `form.rs`) is a page in place of the
  table, not a dialog: it's long and opens dialogs of its own, and its Save/Cancel footer
  (`egui::Panel::bottom`) stays in view while its section cards scroll. Its header, in place of
  the shell's, is a "← Jobs" link over the job's name; that link and Cancel leave a changed form
  only after "Discard changes?". **General**: name, on,
  notify on success, mode (a mirror job shows a warning bar). **Sources**: each folder with its
  exclusions as removable chips and a field to add one. **Targets**: each a box of its own,
  drives picked from the connected volumes (by volume ID and label), shares by UNC path with
  their login (saved to Credential Manager as `share:\\server\share`, one per share: a saved
  one is a chip, "Saved · alex" (its user name, never its password), with Change… and
  Remove; the fields and "Save login" show only when none is saved, or while changing it), and
  for a versioned job the repository password's state (Saved, Missing, or made when it's saved) with "Enter a saved password…" and "Set up now". **Before and after
  steps**: two numbered lists, each with an "Add a step" menu. **Schedule and retention**: a
  picker (`schedule.rs`: by hand, daily, chosen days, an interval, or as typed) that writes
  core's text form, then retention (one "Keep" row: daily, weekly, monthly) or the mirror's
  deletion limit. Messages are core's own (shown with a capital first letter),
  shown next to what they're about (by `job::Problem`), and counted in a bar above Save; one

  "Use a mirror anyway" makes it a mirror (and sets `mirror_deletes_confirmed`).

**The History tab (`ui/history.rs`):** runs and test restores together, newest first,

(`History::runs` / `test_restores` with a `HistoryFilter`, before the limit), the job list is
every job the history has seen (`job_names`), and "Show older" loads another page of 200 of
each kind. A page is cut where one kind may have older entries not loaded yet, so the list
never skips one (`history::paged`).
- **Its layout:** a toolbar (job and result, applied in the history as above; a period
  and a search, over what's loaded, so "Show older" reaches further), a summary line ("6 runs ·

**The Restore tab (`ui/restore.rs`):**

  target isn't connected (as a run would be) and **failed** otherwise (a wrong password, a

  snapshot, which isn't cheap, and the tree reads one folder at a time.

## Packaging and releases

The steps and the manual checklist are in [RELEASING.md](RELEASING.md).

- **The C runtime is linked in** (`.cargo/config.toml`: `+crt-static` for the Windows target),
  so the exes start on a PC without the Visual C++ redistributable (which needs an admin
  install). The linked parts are Microsoft's "Distributable Code" under the Visual Studio
  licence. `crates/replica/tests/packaging.rs` reads both exes' import tables, and `package.ps1`
  the staged ones: no C runtime DLL, and nothing that isn't part of Windows.
- **`scripts/package.ps1`** builds `target\dist\`: `replica-<version>-x64.msi`,
  `replica-<version>-portable.zip` and `SHA256SUMS.txt`. Both packages hold the two exes, the
  pinned restic, `LICENSE.txt` and `THIRD-PARTY-NOTICES.txt`; the zip adds the empty `portable`
  marker. It fails if the notices are out of date.
- **The MSI** (`installer/replica.wxs`, WiX 5): per user, no admin, to
  `%LOCALAPPDATA%\Programs\Replica`; the user's PATH; a Start menu shortcut; the tray started
  with its window open after an interactive install (`--show`; a silent one starts nothing).
  Every MSI removes all earlier installs first, the same version included
  (`AllowSameVersionUpgrades`, `Schedule="afterInstallInitialize"`). **No WiX extension or
  WixUI** (their dialogs, bitmaps and custom-action DLLs are MS-RL and would be embedded):
  Windows shows its own progress. Start with Windows is the
  property `STARTWITHWINDOWS` (on by default), recorded under `HKCU\Software\Replica\Installer`
  and taken into the tray's own setting on its first start (`replica_win::installer::choice`).
- **The tray's installer modes:** `replica-tray.exe --quit` asks a running tray to quit and
  waits for it (a `Local\Replica.Tray.Quit` event beside the instance's Show event;
  `replica_win::tray::request_quit`), before an upgrade or uninstall. `--uninstall` does that,
  then removes Replica's scheduled tasks and its Start with Windows entry. Settings, history,
  logs and backups are never touched. `--show` starts the tray with its window open, as no
  arguments does (a second start asks the running tray to show itself).
- **THIRD-PARTY-NOTICES.txt** (committed): part 1, the Windows build's crates (cargo-about with
  `about.toml` and `about.hbs`, no dev or build dependencies), then the copyright notices of the
  crates whose licence text there is MIT's template ("<year> <copyright holders>", which
  cargo-about gives when a crate ships no filled-in licence): collected by the script from each
  crate as built (its licence files' "Copyright" lines, any other notice file whole, its
  SPDX-FileCopyrightText headers; with none, its `Cargo.toml` authors, said as such), and SQLite
  (public domain, compiled in); part 2, `third_party/restic/NOTICES.txt` from `scripts/audit-restic-licences.py`:
  restic's own licence (from its release source, checked against the release's SHA256SUMS),
  Go's licence and patent grant, every licence and NOTICE file of the linked modules, each text
  once with the modules it covers, and the MPL-2.0 module's exact source.
- **`release.yml`** (on a `v*` tag): the tag must match the version; `cargo deny check`; the tests
  with restic required; `package.ps1`; a **draft** GitHub release with both files,
  `SHA256SUMS.txt` and the changelog's section. Signing is a commented placeholder.

## Tests

[docs/TESTING.md](TESTING.md) is the test policy: what to run when, the tiers, flaky tests and the
rules every test keeps. The suite runs under cargo-nextest, every test its own process
and the test binaries side by side (`.config/nextest.toml`), instead of `cargo test`'s one
binary after another. Tests that can't share what they use take turns in a nextest test group
(`credential-manager`: `credentials.rs`), not an in-process lock, which nextest's processes
don't share.

**Measured** on a 16-thread PC, the default tier: `cargo test --workspace` about 3½
minutes; `cargo nextest run --workspace` 32 s; with `-j 4` 77 s (24 Oct 2026; docs/TESTING.md, Timings). Two waits were trimmed: the
`command_tree` tests that waited out a 15 s and a 20 s step timeout now start at 2 s and lengthen
it only while PowerShell hadn't started (`with_a_started_program`), and the full sweep of a row click
(48 sizes) moved to the stress tier with 12 of them kept in the default tier.
